# 网站闲聊接入与验证 · 2026-10-28

用户要求“网站这块聊天增加个闲聊吧先”。本次实现网站普通回答与提示词创作共存，不修改小程序，也不改既有首页布局。

## 实际行为

- 右侧聊天默认自动判断：问候、闲聊和咨询显示普通正文；明确创作或修改时显示原双语提示词卡片。
- 首页与侧栏统一显示“发送”、使用auto，由同一次模型调用判断普通回复还是生成；不再由首页入口强制generate。首次匿名登录恢复、上传失败后的重试和同key重发保持原意图；退出/401/切账号不自动恢复旧账号私密发送。
- 纯聊天可连续追问；“第二种”等指代包含最近双方对话。生成后聊天再修改，仍能找到最近真正提示词及用户人工编辑的内容。
- 消息轮次与提示词版本分开：普通回答不增加提示词版本号；最新提示词不会因为随后咨询而自动收起。普通回复没有双语切换、编辑提示词或拆解操作。
- 普通正文作为React文本展示，不执行HTML或Markdown。保留原认证/Origin保护、私有no-store、幂等、unknown查询、额度、历史删除/留存与账号切换栅栏。

## 技术栈与接口

前端沿用Next.js 16.4.2、React 19、TypeScript、next-intl、Base UI、Lucide和CSS Modules；后端沿用FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Redis、原独立Worker及OpenAI-compatible模型适配层，无新增Agent框架或UI依赖。

仍使用原`/api/prompt-conversations`创建、消息、详情、历史和删除接口。chat-v2在同一次模型调用内返回原ModelResult或严格reply-1，不先额外调用分类模型；结果保存在既有JSONB，无数据库迁移。普通回复继续占用现有模型调用配额。

| API消息状态 | response_type | assistant_reply | prompt_number | result / prompt |
| --- | --- | --- | --- | --- |
| 普通回复成功 | assistant | 完整正文，1–4000字符 | null | null / null |
| 提示词成功 | prompt | null | 从1连续计数 | 原生成结果/有效中英提示词 |
| 未完成/失败/未知 | null | null | null | null / null |

会话BFF只接受完整合法的新字段组合，旧没有三字段的消息仍兼容。`version`保持消息顺序，续写parent仍指向最新成功消息；不能在客户端跳过闲聊父节点。

## 首页“你好”误生成修复

- 用户实际截图揭示首页入口仍固定`workflow.send("generate")`，侧栏才用auto。只读核对preview库：14:14与14:18的两条“你好”都是`chat-v2 / generate / schema_version=1`，因此是入口强制模式，不是模型将auto问候识别错误。
- 最小修复：首页与侧栏统一`send()`与“发送”按钮；点击和Enter相同。保留API显式generate契约及冻结请求/幂等逻辑，不重写用户旧记录、不偷偷重发旧请求，也不加固定问候关键词表。图片only仍由既有provider规则生成提示词。
- 组件测试先确认3项RED，再GREEN。覆盖首页点击/Enter问候、首次匿名登录恢复，以及图片only、收起后继续原会话；审查未发现登录/账号切换/unknown重复派发回归。
- 本轮恰好2次真实供应商调用，直接使用相同后端`generate_conversation`适配器和既有模型配置，均为`mode=auto`、`max_retries=0`，无图片、无用户会话写入。第1次“你好”→`reply-1`普通回复（2.18秒）；第2次带该回复上下文请求雨夜小猫壁纸→`schema_version=1`中英提示词（12.76秒）。这证明供应商分流质量，不冒称用户Chrome登录会话已由自动化全链路验收。详细结果留存在本地，未纳入仓库。
- 用户3000开发进程与8040真实创作API/Worker保留运行；仅前端改动由开发服务器加载，不重启后端。
